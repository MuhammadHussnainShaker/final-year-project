Project Proposal

Project Title
Event Discovery & Community Engagement Platform

Project Domain / Category
Web Application Development / Event Management System / Community Platform


Abstract / Introduction
The proposed project is a web-based Event Discovery and Community Engagement Platform designed to help users find, explore, and participate in local and online events such as workshops, concerts, sports meets, cultural festivals, networking sessions, and community volunteering drives. The system provides a dynamic and user-friendly interface where users can browse upcoming events displayed both on an interactive map and in a structured list view, helping them decide which events to attend based on location, interest, and date.

This application bridges the gap between event organizers and attendees by combining geographic visualization with structured event data. Users can filter events by category, view event details including venue, schedule, ticket information, and organizer contact, and RSVP or register directly through the platform. The system can be extended to include user reviews, social sharing, and personalized event recommendations, making it a comprehensive and scalable solution for real-world community engagement.


Functional Requirements
FR-01: Interactive Map Display
The system shall display an interactive map interface using a mapping library (such as Leaflet.js or Google Maps API). The map shall load all available events as markers upon page load. Each marker shall be clickable and shall visually distinguish between different event categories using color-coded or icon-based markers. The map shall support zooming, panning, and fitting bounds to show all markers within the viewport.

FR-02: List View of Events
The system shall provide a structured list view displaying all available events retrieved from the backend API. Each list item shall show the event name, category, thumbnail image, date/time, and a short description. The list shall be paginated or infinitely scrollable to handle large datasets efficiently. The list view and map view shall be synchronized so that hovering or clicking a list item highlights the corresponding marker on the map.

FR-03: Category-Based Filtering
The system shall provide a filtering mechanism that allows users to filter events by predefined categories such as Music, Sports, Technology, Art & Culture, Food & Drink, Health & Wellness, and Community Service. The filter shall be accessible via a dropdown menu, tab bar, or sidebar panel. Upon selecting a category, both the map markers and the list view shall update dynamically without requiring a full page reload. Multiple category selection shall be supported where applicable.

FR-04: Event Detail Page
The system shall provide a dedicated detail page for each event, accessible via a unique URL (e.g., /events/:id or /events/:slug). The detail page shall display all available information including the full event name, category, description, venue address, date and time, ticket pricing, organizer contact information, and an embedded mini-map showing the exact event location. The page shall also include a breadcrumb navigation for easy return to the listing page.

FR-05: Images and Descriptions Display
The system shall display one or more images for each event using an image gallery or carousel component. Images shall be lazily loaded to optimize page performance and reduce initial load time. Each event shall include a short description (used in list and featured views) and a full detailed description displayed on the event detail page. Image alt-text shall be included for accessibility compliance.

FR-06: Map Marker Highlighting
The system shall visually highlight the map marker of an event when the user selects it from the list view, search results, or featured section. The highlighted marker shall change its icon, size, or color to distinguish it from unselected markers. The map shall automatically pan and center on the selected marker if it is outside the current viewport. A popup or tooltip shall appear displaying the event name, date, and category.

FR-07: Featured Events Section
The system shall include a dedicated Featured Events section displayed prominently on the homepage or landing page. Featured events shall be manually selected and managed by the admin through the Strapi CMS dashboard. Each featured event card shall display the event name, category, thumbnail image, date, short description, and a "View Details" button linking to the full detail page. The section shall be displayed in a responsive card grid or horizontal scrollable carousel layout.

FR-08: Search Functionality
The system shall provide a search bar that allows users to search for events by name, category, organizer, or venue keyword. Search queries shall be sent to the backend API, which shall return matching results from the database. Search results shall be displayed in real time or upon submission, updating both the list view and the map markers accordingly. The search bar shall include a clear/reset button to restore the default view. If no results are found, a user-friendly "No results found" message shall be displayed.

FR-09: Address and Basic Details Display
The system shall display the full address of each event venue including street, city, and region where available. Basic details such as event date, time, category label, ticket price (or 'Free'), and organizer contact shall be visible in both the list card and the detail page. The address shall be formatted consistently across all views and shall optionally include a "Get Directions" link that opens the venue in Google Maps or a native map application.

FR-10: Responsive Interface
The system shall provide a fully responsive user interface that adapts seamlessly to all screen sizes including mobile phones, tablets, and desktop monitors. The layout shall follow a mobile-first design approach using Tailwind CSS breakpoints. On mobile devices, the map and list view shall be toggled via a tab or floating button rather than displayed side by side. All interactive elements including buttons, filters, and search inputs shall be touch-friendly with appropriate tap target sizes as per accessibility guidelines.


The Three Core Roles
Role 1: Guest User (Unauthenticated)
This is any visitor who accesses the application without logging in.

What they CAN do:
    • Browse the interactive map and view all event markers
    • View the list of all available upcoming and past events
    • Filter events by category, date range, or location
    • Use the search functionality to find specific events
    • View event detail pages (name, description, images, venue, schedule)
    • View the featured events section on the homepage

What they CANNOT do:
    • RSVP or register for events
    • Submit reviews or ratings
    • Create or submit new events
    • Access any admin or management features

In Strapi: This maps to the Public role, which has read-only access to published event data via the API.

Role 2: Registered User (Authenticated)
This is a visitor who has created an account and logged in via NextAuth.js + Strapi authentication.

What they CAN do:
    • Everything a Guest User can do
    • RSVP or register for events and receive confirmations
    • Save or bookmark favorite events to their profile
    • Submit reviews and ratings for events they have attended
    • View their personal profile, RSVP history, and saved events list
    • Update their own account information (name, password, profile picture)
    • Submit a new event for admin review and approval

What they CANNOT do:
    • Edit or delete other users' data
    • Publish or approve submitted events
    • Access the admin dashboard
    • Manage categories or system settings

In Strapi: This maps to the Authenticated role, which has read access to all public data plus write access to their own user-specific data such as RSVPs, favorites, and reviews.

Role 3: Administrator (Admin)
This is a trusted internal user who manages all content and system settings through the Strapi CMS admin dashboard.

What they CAN do:
    • Full CRUD (Create, Read, Update, Delete) access to all events
    • Add, edit, or remove event images, descriptions, venues, and schedules
    • Create, edit, and delete event categories
    • Mark or unmark events as 'Featured' for the homepage section
    • Manage all registered user accounts (view, activate, deactivate, delete)
    • Approve or reject user-submitted event listings
    • Manage roles and permissions for other users
    • Configure API access and content visibility settings
    • Access usage analytics and system logs (if enabled)

What they CANNOT do:
    • Actions are limited only by system-level server configurations outside Strapi

In Strapi: This maps to the Super Admin or a custom Admin role created inside the Strapi admin panel with full collection-level permissions.


Key Features
    • Dynamic event content management via Headless CMS
    • User authentication, authorization, and role-based access control
    • Fully responsive design across all devices
    • SEO optimization with meta tags and structured data
    • Image optimization and lazy loading for performance
    • Real-time data synchronization between map and list views
    • RSVP and event registration with confirmation notifications
    • Admin dashboard for complete content and user management

Scope of Project:
People usually discover events through sources such as social media posts, WhatsApp groups, posters, university notices, and personal contacts. This creates difficulty for users because complete information about event location, date, timing, category, organizer contact, and registration method is often not available in one place. On the other side, event organizers also need a proper platform where they can publish events and reach interested attendees in an organized way.
In this context, the project aims to develop a web-based application named “Event Discovery & Community Engagement Platform”. The system will provide a centralized platform where users can discover local and online events such as workshops, concerts, sports activities, cultural festivals, networking sessions, technology sessions, food events, health and wellness activities, and volunteering drives. Users will be able to browse approved events through list view and map view, search events, apply filters, view complete event details, RSVP for events, save events for later, and submit new events for administrator approval.
The Administrator will manage the event content of the platform. Administrator will be able to create, update, delete, approve and reject events, manage categories, manage featured events and review user-submitted events. The system will ensure proper role-based access so that Guest Users can only browse public content, Registered Users can participate and submit events, and Administrators can manage the system.
The system will focus on usability, security, reliability, maintainability, performance and compatibility so that event discovery and community engagement can be performed smoothly through a web-based environment.
Timeline: The project should be completed on or before October 27, 2026.

NFR05: The system shall use authentication, authorization, password protection, and input validation to prevent unauthorized access and invalid data submission.
5. Reliability:
NFR06: The system shall save and retrieve event data, user accounts, RSVP records, saved events, and approval decisions consistently without crashing.
6. Maintainability:
NFR07: The system shall be developed in a modular and scalable way so future changes such as new categories, reviews, or notifications can be added easily.

NFR08: The system shall be compatible with common modern browsers and usable on desktop, tablet, and mobile devices.

Adopted Methodology

Available Methodologies:
Some common software development methodologies (software models) are:
    1. Waterfall Model
    2. Prototyping Model
    3. Spiral Model
    4. RAD Model
    5. VU Process Model (Combination of Waterfall and Spiral models)

    1. Waterfall Model:
It is a linear model. As name indicates, it is a sequential model like a waterfall, in which each new phase starts only when the previous one is completed. This model is best suited for a software whose requirements are well understood and stable. This model includes following phases.
    (i) Requirements Analysis: Requirements are gathered and analysed for development of technical specifications. 
    (ii) System Design: System is designed according to software requirement specifications developed in previous phase.
    (iii) Development/Implementation: System design prepared in previous phase is implemented in this phase to develop the code of the product.
    (iv) Integration and Unit/System/User Acceptance Testing: Integration of the system components and rigorous testing of the whole system to check whether it meets the requirements.
    (v) Deployment: In this phase, the developed system is deployed on client side.
    (vi) Maintenance: Any updates to adapt any changes or addition in the requirements of the system in future.


Figure 1.1 (Waterfall Model)



    2. Prototyping Model:
If the requirements of the software are not well understood or prone to changes later, then an early version (prototype) of the software is developed in a short span of time. That prototype is then refined multiple times until a required standard is achieved. This process is called prototyping model. This includes following phases:
    (i) Requirement Gathering: Basic requirements are gathered from the customer.
    (ii) Quick Design: A quick design is created on the basis of initial requirements, focusing on major functionality.
    (iii) Prototype Development: A prototype of the system is built using rapid development tools, presenting the core functionality.
    (iv) Prototype Evaluation: Prototype is presented in front of stakeholders for feedback, and they suggest any improvements or changes.
    (v) Refinement: Prototype is refined, and on the basis of feedback, features are modified, added or removed. 
    (vi) Repeat: The cycle of prototype development, evaluation and refinement is repeated until a satisfactory prototype is achieved.
    (vii) System Development: Finally, when the prototype is approved from the stakeholders and requirements are finalized, then actual development of the system starts in this phase.
 

Figure 1.2 (Prototyping Model)

    3. Spiral Model:
This model combines the systematic nature of waterfall model and iterative development. This model is used for the development of large-scale, complex, unclear, uncertain and high risk softwares, such as, missile guidance system. Structured nature of waterfall model is used to manage risk and iterative development is used to adapt any changes throughout the lifecycle.
Steps involved in spiral model are:
    (i) Planning: Objective, requirements, constraints, project scope, deliverables, resource allocation, scheduling, alternative solutions and strategies are identified.
    (ii) Risk Analysis: Potential risks are identified and their impact on project objectives is assessed. Based on that assessment, risk mitigation plan is developed to manage the risk throughout the lifecycle.
    (iii) Engineering: Development activities are conducted for the requirements gathered in the planning phase. Prototype development may be used for the validation of requirements and design. Reviews are held to assess progress and tackle any deviation.
    (iv) Evaluation: The current iteration is evaluated for completeness, as per features, quality and objectives. On the basis of feedback of stakeholders and lessons learnt from that iteration, any changes or improvements in project plan amd requirements are incorporated in the next iterations.


Figure 1.3 (Spiral Model)

	Key Features of Spiral Model:
    (i) Iterative approach: Despite of developing the whole system at once, system is divided into iterations/spirals, all the steps repeated in each spiral.
    (ii) Risk Management: Risk is analysed at the start of each iteration and risk mitigation plan is developed.
    (iii) Progressive Elaboration: In each iteration, understanding about the requirements became more and more clear, resulting in reduced uncertainty.
    (iv) Flexibility: Fexible due to its spiral nature, as changes can be accommodated at each iteration.

    4. RAD Model:
Rapid Application Development is a software model in which system is developed, rapidly, component wise (each component by a separate team in parallel) to speed up the process.
It combines iterative development and prototyping. Prototypes are developed initially for requirement validation and then improved on the basis of stakeholders feedback. This model is adopted, if requirements are uncertain or time to deliver is short.
Activities involved in RAD are:
    (i) Business Modeling: Essential business processes, goals and requirements are documented rapidly through interviews, workshops and other techniques. Here, prototypes may also be used for requirement validation.
    (ii) Data Modeling: Systems’s data architecture is designed to define the data requirements to fulfil business needs including databases, tables and relationships. Entity-Relationship Diagrams and other data models are designed for data validation and feedback.
    (iii) Process Modeling: It involves documenting the flow of activities in the system, and their interactions. Process diagrams and flowcharts etc. are developed to visualize the flow of system. Prototyping is used for validation of process models according to business requirements.
    (iv) Application Generation: In this phase, application is developed rapidly based on the requirements, designs and process models established in previous phases. Different teams work on each component in parallel to speed up the process.
    (v) Testing: System components are tested throughout the lifecycle using proper test coverage. Testing is incorporated in each phase of the SDLC, in which developer and user both work together to test the developed component or system.
    (vi) Turnover: Also known as deployment or implementation, system is continuously deployed into production for operational use throughout lifecycle for rapid delivery, and improving it later in next iterations.


Figure 1.4 (RAD Model)




    5. VU Process Model (My Adopted Methodology):
I will adopt VU Process Model for the development of this project because it is a combination of Waterfall and Spiral models. So, it will include structured approach of waterfall model as well as iterative nature of spiral model.
    • Using waterfall nature, I can build the system using a structured and well-defined approach. Due to linear nature of waterfall model, it will be easy to develop the product phase by phase.
    • Using Spiral nature, I can perform risk analysis at the start of each phase, verification at the end of each phase, and iterative development, resulting in an efficient and reliable product.
	Key features of VU Process Model are:
    (i) Sequential Phases:
Just like waterfall model, VU process model follows the linear approach in which each phase must be completed before the start of next phase. It makes the VU Process Model, a structured model, very useful for systematic development throughout the lifecycle.
    (ii) Risk Management:
Risk analysis at the start of each phase is very beneficial for risk management and mitigation. Risk is analyzed before starting of each phase, and then a mitigation plan is developed to create a reliable product. 
    (iii) Verification and Validation:
Verification is performed at the end of each phase, so that the work done at each phase can be verified and validated before moving to the next phase. So, defects are prevented to pass on to the next phases. As a result, cost to remove errors at later stages will also be minimized.
    (iv) Iterative Development:
Being combination of both waterfall and spiral models, VU process model is an iterative model, just like spiral model. It incorporates iterative software development practices to improve/update/change the product continuously throughout the lifecycle. Feedback is gathered at each phase and corresponding changes are made reducing the product failure chances at later stages.
    (v) Documentation:
Similar to waterfall and spiral model, VU process model emphasizes comprehensive documentation of each phase of the lifecycle. This documentation will serve as a reference for all the stakeholders and help to understand the progress of the project as valuable insights.
    (vi) Flexibility:
Being a combination of both waterfall and spiral model, it provides a lot of flexibility to adapt to any changes/updates, if any change occurs in the requirements, scope or objective of the product.



    (vii) Traceability:
VU process model emphasizes traceability in all phases of the software development lifecycle to ensure that requirements are reflected in design, implementation, testing and maintenance etc. It results in consistency throughout the project to make any changes, when required.




Figure 1.5 (VU Process Model)
